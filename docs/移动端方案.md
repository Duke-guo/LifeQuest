# 手机版（移动端）技术方案 · 草案 v1

> 目标：回答「能不能做成手机版、怎么做、要花多大代价」。
> 本文是方案，不含代码改动。核心结论先行：
> **能做，Vue 界面层可复用约八成；真正的硬骨头是「本地文件」这一数据底座要换，以及手机↔电脑的数据同步。**

---

## 1. 现状回顾（为什么这决定了方案）

| 层 | 现状 |
|---|---|
| 界面 | Vue 3 + Pinia + Vite，9 个视图（首页/任务/日历/笔记/日记/计划/赛季/知识地图/主线地图） |
| 数据 | 全部走 `services/data.ts` 里的 **`dataApi` 对象**（读/写 JSON、Markdown、图片、附件、导出、AI 识图） |
| 后端 | Electron 主进程 `ipcMain.handle('data:*')` → `dataStore.ts` 操作磁盘 `LifeQuest-Data/` |
| 数据形态 | 普通文件：`config/*.json`、`tasks/tasks.json`、`plans/plans.json`、`journal/*.md`、`notes/*.md`、`assets/`、`archive/` |

关键点：**所有上层代码（store、视图、组件）只依赖 `dataApi` 这一个接口**。这意味着一件很划算的事——只要给 `dataApi` 写一个「手机版实现」，上面的界面几乎原样就能跑。

---

## 2. 核心矛盾：本地文件 vs 手机沙盒

- 桌面版卖点是「数据就是你能看见的普通文件」。
- 手机上（iOS/Android）App 被关在沙盒里，**不能在用户可见的位置自由铺文件夹**，只能：
  1. 存 **App 私有目录**（用户看不到，但可通过「导出/备份」变成文件）；
  2. 存 **浏览器本地存储**（PWA 的 IndexedDB/OPFS）。

结论：手机版把「本地优先」重新表达为——**数据仍只存在这台设备里、不联网、可导出成文件带走**，而不是「用户随时在文件管理器里翻得到」。

---

## 3. 三条路线对比

| | A. PWA | B. Capacitor | C. Tauri/原生重写 |
|---|---|---|---|
| 是什么 | 网页应用，加到主屏当 App 用 | 同一套 Vue + 原生壳打包 | 用别的语言重写 |
| 复用现有代码 | 高（约 80%） | 高（约 85%） | 低 |
| 上架商店 | 不需要（也可能上） | 能上 App Store / 应用商店 | 能 |
| iOS 文件系统能力 | 受限（导出要绕） | 好（原生文件） | 好 |
| 工程量 | 中 | 中高 | 高 |
| 结论 | **推荐先做** | 二阶段可选 | 不推荐 |

**推荐路径**：A 先行验证 → 需要上架或更强原生能力时，PWA 的界面层可直接被 B 复用（几乎不返工）。

---

## 4. 数据底座设计（手机版）

做一个 **虚拟文件系统（VFS）**，保持「一切都是文件」的心智模型，让 `dataApi` 的语义原样落地：

- 底层：**IndexedDB**（一个 `files` 对象存储，键=相对路径，值=`{ content, mtime }`）
  - 文本文件存字符串；图片/附件存 `Blob`/`Uint8Array`
- 上层：`dataApi` 的同名方法 1:1 映射到 VFS：
  - `readJson/writeJson` → 读写 `config/xxx.json`
  - `readMarkdown/writeMarkdown` → 读写 `journal/…`、`notes/…`、`archive/…`
  - `listFiles/deleteFile` → 遍历/删除 VFS
  - `saveImage/readImage` → 存/取 Blob
- **导出 = 把整个 VFS 打成 zip 下载**；**导入 = 解 zip 写回 VFS**（正好复用桌面版已有的导出格式）

这样桌面版与手机版**共用同一套 `dataApi` 接口定义**，只是各自一个实现。

## 5. 功能取舍（哪些原样、哪些改、哪些砍）

| 功能 | 手机版处理 |
|---|---|
| 日记 / 日历 / 任务 / 笔记 / 计划 / 赛季·成就·回顾 / 知识地图 / 主线地图 / 每页帮助 / 示例数据 | **原样复用**，只做移动端布局适配 |
| 标题栏 / 窗口拖拽 / 最小化最大化 | 砍掉（网页无窗口概念） |
| 附件（attachFile） | 改成手机「选文件/相册」（`<input type=file>` / 分享入口） |
| 导出 / 导入 | 导出 zip / 选 zip 导入（浏览器下载/上传） |
| 提醒（ReminderBanner） | PWA 用 Notification API（iOS 弱）；Capacitor 用本地通知 |
| AI 识图 | 浏览器直接调 DeepSeek 可能有 CORS 问题 → 见 §7 |

## 6. 数据同步（最难的一道题）

手机和电脑是**两份数据**。选项：

1. **v1 手动搬家（推荐先做）**：手机「导出 zip」→ 通过云盘/微信发给电脑 → 电脑「导入」。诚实、零后端、贴合本地优先。
2. **v2 WebDAV**：把 VFS 指向一个 WebDAV 目录（坚果云 / Nextcloud / 自建），手机电脑读写同一处。中等工程量，真正的同步。
3. **自建云**：个人项目不建议。

> 建议：第一版**不做自动同步**，先保证「手机记的能导出来、电脑能导进去」，把体验跑顺再谈 WebDAV。

---

## 7. 风险与待验证点（技术预研要确认）

1. **iOS Safari 的持久化**：PWA 数据存在 IndexedDB，系统空间紧张时可能被清理——需实测，必要的话提示用户「导出备份」。
2. **AI 识图 CORS**：DeepSeek 接口是否允许浏览器跨域调用；不行就 v1 先只在桌面版提供 AI 识图，或加一个免费代理。
3. **离线与更新**：PWA 的 manifest/service worker，保证「加到主屏」后像个 App、能离线打开。
4. **字体/中文渲染**：手机端已验证的中文字体与现有视觉风格要重新看一眼。

---

## 8. 分阶段实施（建议）

| 阶段 | 内容 | 目标 |
|---|---|---|
| P0 | 本方案 + 技术预研（验证 IndexedDB VFS、iOS 持久化、AI CORS） | 确认可行 |
| P1 | 抽离 `dataApi` 接口 → 实现 IndexedDB VFS → 最小 PWA（首页/任务/日历/日记能跑、数据本地保存、可导出 zip） | 手机上能记录 |
| P2 | 补全其余模块 + 移动端布局 + 加到主屏 + 图标/离线 | 接近完整可用 |
| P3 | （可选）AI 识图代理、通知、WebDAV 同步、转 Capacitor 上架 | 进阶 |

**工程量**（个人业余时间估算，非承诺）：P1 是主体工程，约 1–2 周；P2 再 1–2 周；P3 视范围。

## 9. 待你拍板

1. **手机上主要用它做什么**？（记任务？写日记？看课表？）—— 决定 MVP 先做哪几块
2. **同步**：接受 v1「导出/导入 zip 手动搬家」吗？还是上来就要 WebDAV 自动同步？
3. **AI 识图**：手机上需要吗？
4. **上架**：将来想上 App Store / 应用商店吗（决定要不要走 B 路线）？

这四点定了，P0 预研就能有明确靶子。
